{{ if or .Values.seed.clients .Values.adminGateway.enabled -}}
FIRST-BOOT CREDENTIALS. This release mints credentials that are shown once and
   never again -- a seeded client secret per client{{ if .Values.adminGateway.enabled }}, the admin gateway's super_admin
   bootstrap password{{ end }}, and the admin token when secrets.keys.adminToken is unset.
   They are deliberately not in the pod log. They are written to
   {{ .Values.firstBootCredential.path }} inside the pod, mode 0600.
{{- if not .Values.firstBootCredential.existingClaim }}

   That volume is memory-backed, so it is gone when the pod is. Read it before
   anything restarts the pod, or set firstBootCredential.existingClaim to a
   PersistentVolumeClaim and read it from there at your leisure.
{{- end }}

   The image is distroless, so it has no shell to `kubectl exec cat` with and no
   tar for `kubectl cp`. Attach an ephemeral container that can see its
   filesystem, then read the file over `kubectl exec`. Two commands, and the
   reason for that is below them:

     POD=$(kubectl get pod -n {{ .Release.Namespace }} -o name \
       -l app.kubernetes.io/name={{ include "vault.name" . }},app.kubernetes.io/instance={{ .Release.Name }},app.kubernetes.io/component=vault \
       | head -1)

     kubectl debug -n {{ .Release.Namespace }} $POD --image=busybox --target={{ .Chart.Name }} \
       --profile=general --container=cred-reader --attach=false -- sleep 600

     kubectl exec -n {{ .Release.Namespace }} $POD -c cred-reader \
       -- cat /proc/1/root{{ .Values.firstBootCredential.path }}

   A Pod, not deploy/{{ include "vault.fullname" . }}: `kubectl debug` attaches an ephemeral
   container, which only a Pod can hold, and the Deployment form fails with
   `error: "apps/v1, Kind=Deployment" not supported by debug`.

   And `sleep`, not `cat`. An ephemeral container's command writes to that
   container's stdout, and that stdout is a container log, so
   `kubectl debug ... -- cat` puts the credential straight into
   `kubectl logs $POD -c cred-reader` and from there into whatever scrapes this
   cluster -- which is the exposure the 0600 file exists to avoid. `kubectl exec`
   streams to your terminal instead: the API server records that an exec
   happened, never what it carried. Dropping -it does not help; cat writes to
   that stdout either way.

   IF YOU HAVE ALREADY RUN A FORM THAT PRINTED IT -- `kubectl debug ... -- cat`,
   or an `-it` session where the value appeared on screen -- the credential is in
   the cluster's logs and has to be treated as disclosed. Rotate it: the admin
   token with `vault rotate-admin-token`, a client secret with
   `vault rotate-client-secret`{{ if .Values.adminGateway.enabled }}, the super_admin password by logging into the
   admin gateway and changing it{{ end }}. Deleting the pod does not remove the log record.
{{- if gt (int .Values.replicaCount) 1 }}

3. Register a client:
  ADMIN_TOKEN=$(kubectl get secret -n {{ .Release.Namespace }} {{ include "vault.secretName" . }} \
    -o jsonpath='{.data.{{ .Values.secrets.keys.adminToken }}}' | base64 -d)
  kubectl exec -n {{ .Release.Namespace }} deploy/{{ include "vault.fullname" . }} -- \
    /app/vault add-client --admin-token "$ADMIN_TOKEN" \
    --name "frontend" --role "frontend" --scopes "user:read,user:write"

  The binary is /app/vault; the path printed here used to be /vault, which is
  where it is built, not where the image puts it. The token is read on your own
  machine because the previous form expanded $(cat /run/secrets/...) there too,
  against a file that only exists in the pod, and the image is distroless, so
  there is no shell in the pod to expand it in either.

  --admin-token puts the token in the argument list of the process it starts,
  readable from /proc/<pid>/cmdline by anything sharing that pod's PID namespace
  for as long as the command runs, and left in your shell history by the line
  above. Prefer the admin gateway for anything routine.
